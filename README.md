# Data Platform Operations Lab — эксплуатация платформы данных в Kubernetes

## Цель проекта

Создать учебный стенд для решения основной задачи работодателя: **поддерживать работоспособность платформы данных в Kubernetes, настраивать мониторинг, диагностировать проблемы и автоматизировать обслуживание**.

Самостоятельно подготовить инфраструктуру, развернуть объектное хранилище и Apache Spark, создать небольшие учебные данные и вычислительное задание. Затем настроить мониторинг, выполнить обновление компонента и автоматизировать операции с объектами через GitLab CI.

Отдельно освоить развёртывание и обновление Kubernetes через Ansible и Kubespray.

**Исходные условия:** у преподавателя и студентов нет готового стенда, конфигураций, учебных данных или заданий Spark. Всё это создаётся в рамках проекта по последовательным инструкциям.

**Формат реализации:** основная часть выполняется в локальном Kubernetes, запущенном внутри Docker. GitLab Runner запускается локально, а репозиторий и задания CI размещаются в доступном GitLab. При наличии университетского GitLab используется он.

**Интернет:** необходим для первоначального получения программ, образов и зависимостей. При использовании внешнего GitLab интернет нужен также для выполнения заданий CI. Полностью автономный режим требует отдельной подготовки локального GitLab и всех зависимостей.

**Ограничение ресурсов:** Kubernetes, Spark, хранилище и мониторинг потребляют существенные ресурсы. На слабом компьютере компоненты запускаются последовательно, а совместные эксперименты выполняются на одном более мощном компьютере группы. Возможность одновременного запуска проверяется на первом этапе.

**Отдельный модуль:** задания Kubespray выполняются на виртуальных машинах. Локальный Kubernetes внутри Docker не заменяет практику установки кластера через Kubespray.

**Статус:** описание проекта для реализации. Команды, конфигурации и сценарии предстоит создать и проверить в ходе выполнения. Этот текст не является готовым комплектом запуска.

### Полученные навыки

После выполнения проекта:

* Эксплуатация компонентов платформы данных в Kubernetes.
* Установка и обновление компонентов через Helm.
* Работа с S3-совместимым объектным хранилищем.
* Запуск и диагностика заданий Apache Spark.
* Настройка мониторинга состояния и нагрузки.
* Поиск причин ошибок и нехватки ресурсов.
* Автоматизация копирования и очистки данных через GitLab CI.
* Развёртывание и обновление Kubernetes через Kubespray.
* Использование переменных Ansible и понимание их приоритетов.
* Проверка работоспособности после изменений.

### Используемые инструменты

| Инструмент                                          | Назначение                                                              |
| --------------------------------------------------- | ----------------------------------------------------------------------- |
| **Kubernetes**                                      | Размещение компонентов платформы данных.                                |
| **Helm**                                            | Установка, настройка и обновление компонентов.                          |
| **S3-совместимое хранилище**                        | Хранение входных данных и результатов вычислений.                       |
| **Apache Spark**                                    | Выполнение учебного задания и диагностика вычислительной нагрузки.      |
| **GitLab CI, GitLab Runner**                        | Автоматизация операций обслуживания.                                    |
| **Prometheus, Grafana**                             | Учебная реализация мониторинга; работодатель конкретный стек не назвал. |
| **Ansible, Kubespray**                              | Развёртывание и обновление отдельного Kubernetes-кластера.              |
| **Linux**                                           | Среда работы и обслуживания узлов.                                      |
| **Docker и средство запуска локального Kubernetes** | Вспомогательные инструменты для воспроизведения стенда на компьютере.   |

Hadoop / HDFS рассматриваются при изучении старой платформы работодателя. Развёртывание отдельного Hadoop-кластера в основной проект не входит.

## Этапы выполнения

**Порядок обучения:** подготовить среду → запустить минимальную платформу → выполнить вычисление → наблюдать → диагностировать → автоматизировать → обновить.

Каждый этап включает небольшое действие, проверку результата и сохранение созданных файлов. Задания не требуют заранее подготовленных преподавателем образов, данных или конфигураций.

### 1. 🟢 Подготовить рабочую среду

Проверить доступные ресурсы компьютера, возможность использования виртуализации и доступ в интернет.

Установить:

1. Docker.
2. Клиент Kubernetes — `kubectl`.
3. Helm.
4. Средство запуска Kubernetes внутри Docker.
5. Git.

На Windows подготовить Linux-среду, необходимую для выбранного способа работы с контейнерами.

Создать папку проекта и файл README. Записать установленные версии программ.

**Проверка:** Docker запускает тестовый контейнер; остальные инструменты выводят свои версии.

*Скриншот 1: успешный запуск контейнера и версии инструментов.*

### 2. 🟢 Создать локальный Kubernetes-кластер

Создать минимальный кластер внутри Docker.

Выполнить четыре действия:

1. Проверить готовность узла.
2. Посмотреть системные Pod.
3. Создать пространство имён проекта.
4. Проверить доступные ресурсы.

Сохранить конфигурацию создания кластера в папке проекта.

**Проверка:** узел имеет состояние `Ready`, системные компоненты работают, пространство имён создано.

*Скриншот 2: готовый узел и пространство имён проекта.*

### 3. 🟢 Описать архитектуру платформы

Создать в README небольшую таблицу.

| Архитектура                 | Где находятся данные                                 | Где выполняются вычисления                          |
| --------------------------- | ---------------------------------------------------- | --------------------------------------------------- |
| Hadoop / HDFS               | В распределённой файловой системе на узлах хранения. | Вычисления могут размещаться ближе к блокам данных. |
| Spark и объектное хранилище | В S3-совместимом хранилище.                          | Spark получает данные через API хранилища.          |

Объяснить своими словами:

* Для чего нужны распределённые системы хранения.
* Что означает data locality.
* Почему объектное хранилище может работать внутри организации.
* Почему производительность зависит от архитектуры, ресурсов и характера нагрузки.

**Проверка:** студент объясняет назначение Spark, хранилища и Kubernetes без смешения их функций.

*Скриншот 3: таблица и описание архитектуры.*

### 4. 🟢 Развернуть объектное хранилище

Выбрать доступное S3-совместимое хранилище и получить его образ и документацию.

Создать минимальные файлы конфигурации:

1. Параметры запуска.
2. Учебные учётные данные через Kubernetes Secret.
3. Подключение постоянного тома.
4. Service для доступа.
5. Способ подключения с компьютера.

Развернуть хранилище. Создать отдельный учебный бакет.

**Проверка:** хранилище доступно, бакет создан, данные размещаются на подключённом томе.

*Скриншот 4: работающий компонент и учебный бакет.*

### 5. 🟢 Создать учебные данные

Самостоятельно создать небольшой CSV-файл с тремя столбцами:

```csv
department,day,operations
analytics,2026-01-01,120
risk,2026-01-01,80
analytics,2026-01-02,150
risk,2026-01-02,90
```

Загрузить файл в хранилище, скачать обратно и сравнить содержимое.

Использовать только искусственные данные.

**Проверка:** файл доступен в бакете, скачанная копия совпадает с исходной.

*Скриншот 5: загруженный объект и его содержимое.*

### 6. 🟡 Запустить минимальное задание Spark

Подготовить минимальное окружение Spark для запуска в Kubernetes. Проверить совместимость Spark и библиотек доступа к выбранному S3-хранилищу.

Создать короткое учебное задание:

1. Прочитать CSV из хранилища.
2. Сгруппировать записи по подразделению.
3. Посчитать сумму операций.
4. Сохранить результат в отдельный префикс хранилища.

Ожидаемый результат:

| Подразделение | Сумма операций |
| ------------- | -------------: |
| analytics     |            270 |
| risk          |            170 |

Сохранить код задания, параметры подключения и способ запуска в проекте. Учётные данные хранить отдельно от кода.

**Проверка:** Spark завершил вычисление, результат совпадает с контрольными значениями.

*Скриншот 6: журнал успешного задания и результат расчёта.*

### 7. 🟡 Научиться находить состояние и журналы

На уже работающем задании выполнить:

1. Найти Pod driver и executor.
2. Посмотреть их состояние.
3. Открыть журналы.
4. Найти события Kubernetes.
5. Определить, где искать причину неуспешного запуска.

Добавить в README короткую памятку диагностики.

**Проверка:** студент самостоятельно находит статус задания и относящиеся к нему сообщения.

*Скриншот 7: состояние задания и соответствующий журнал.*

### 8. 🟡 Изменить конфигурацию через Helm

Оформить уже работающую конфигурацию одного компонента в небольшой Helm-чарт либо использовать подходящий существующий чарт.

Начать с одного параметра:

1. Вынести ограничение памяти в `values.yaml`.
2. Проверить сформированные манифесты.
3. Применить чарт.
4. Изменить значение.
5. Выполнить обновление.

Повторить контрольную операцию с хранилищем или задание Spark.

**Проверка:** новое значение применилось, выбранный компонент продолжает работать.

*Скриншот 8: параметр Helm и фактическая конфигурация Pod.*

### 9. 🟡 Настроить минимальный мониторинг

Установить Prometheus и Grafana с настройками, подходящими ресурсам стенда.

Последовательно вывести на панель:

1. Использование CPU.
2. Использование памяти.
3. Перезапуски Pod.
4. Состояние компонентов.

Запустить задание Spark и отметить период его выполнения на графиках.

**Проверка:** показатели поступают; студент объясняет, какие компоненты использовали ресурсы во время расчёта.

*Скриншот 9: панель мониторинга во время выполнения задания.*

### 10. 🟠 Самостоятельно создать и устранить ошибку Spark

Скопировать рабочую конфигурацию задания и изменить путь к входному файлу на несуществующий.

Затем:

1. Запустить задание.
2. Найти ошибку в журнале.
3. Проверить наличие объекта в хранилище.
4. Исправить путь.
5. Повторить запуск.

**Проверка:** причина ошибки подтверждена; после исправления результат снова совпадает с контрольным.

*Скриншот 10: ошибка чтения и успешный повторный запуск.*

### 11. 🟠 Воспроизвести нехватку ресурсов Kubernetes

В копии конфигурации задать запрос ресурсов, превышающий доступные ресурсы учебного узла.

Выполнить:

1. Запустить задание.
2. Найти ожидающий Pod.
3. Посмотреть события планирования.
4. Сравнить запрос с ресурсами узла.
5. Уменьшить запрос до подходящего значения.
6. Повторить запуск.

**Проверка:** студент объясняет причину состояния `Pending` и подтверждает её сообщением Kubernetes.

*Скриншот 11: событие планирования и работающий Pod после исправления.*

### 12. 🟠 Исследовать нагрузку Spark

Увеличить объём искусственных данных с помощью небольшого генератора. Подобрать объём, который безопасно помещается в ресурсы стенда.

Выполнить два запуска:

1. С исходными настройками Spark.
2. С изменённым числом executor или другой одной настройкой ресурсов.

Записать:

* Объём входных данных.
* Настройки запуска.
* Время выполнения.
* Потребление CPU и памяти.
* Наличие ошибок.

**Проверка:** получено измеренное сравнение. Вывод учитывает и скорость, и расход ресурсов; улучшение не предполагается заранее.

*Скриншот 12: таблица результатов и графики двух запусков.*

### 13. 🟠 Подготовить GitLab CI для обслуживания

Создать проект в доступном GitLab и установить GitLab Runner.

Настроить Runner так, чтобы выполняемые им задания могли обращаться к учебному хранилищу.

Создать первый `.gitlab-ci.yml` с одним заданием:

1. Подключиться к хранилищу.
2. Получить список объектов учебного бакета.
3. Вывести результат без учётных данных.

Добавить доступы в переменные CI.

**Проверка:** задание запускается в GitLab и получает список учебных объектов.

*Скриншот 13: успешное задание и список объектов.*

### 14. 🟠 Автоматизировать копирование данных

Сначала скопировать учебный объект вручную из одного префикса в другой.

Затем создать сценарий и подключить его к GitLab CI.

Передавать через параметры:

1. Исходный префикс.
2. Префикс назначения.
3. Имя учебного бакета.

Добавить проверку существования и содержимого полученного объекта.

**Проверка:** копирование выполняется через CI, результат подтверждён проверкой данных.

*Скриншот 14: успешное копирование и объект в месте назначения.*

### 15. 🟠 Автоматизировать очистку версий объектов

Создать отдельный учебный бакет с версионированием.

Несколько раз загрузить изменённый тестовый файл под одним именем. Убедиться, что появились разные версии.

Создать сценарий:

1. Получить список версий.
2. Выбрать устаревшие версии по заданному условию.
3. Показать предварительный список удаления.
4. Удалить выбранные версии только из учебного бакета.
5. Проверить сохранность текущей версии.

Подключить сценарий к GitLab CI. После успешной ручной проверки добавить запуск по расписанию.

**Проверка:** удалены только выбранные устаревшие версии; текущие данные доступны.

*Скриншот 15: предварительный список и результат очистки.*

### 16. 🟠 Проверить обновление компонента

Выбрать компонент и изучить условия совместимости его текущей и целевой версий.

До обновления:

1. Сохранить текущие параметры Helm.
2. Проверить состояние компонента.
3. Выполнить контрольную операцию.
4. Определить способ восстановления при неудаче.

Выполнить обновление через Helm. Проверить журналы, состояние Pod, метрики и повторить контрольную операцию.

Для первого опыта выбрать обновление без необратимого изменения формата данных.

**Проверка:** целевая версия работает; результат контрольной операции и влияние обновления записаны.

*Скриншот 16: новая версия и успешная проверка работоспособности.*

### 17. 🔴 Подготовить отдельный стенд Kubespray

Создать Linux-виртуальные машины по требованиям выбранной версии Kubespray.

Самостоятельно подготовить:

1. Сетевую связность между машинами.
2. SSH-доступ.
3. Необходимые права пользователя.
4. Окружение Ansible.
5. Inventory с адресами и ролями узлов.

Зафиксировать совместимые версии и параметры машин в README.

На небольшом отдельном playbook проверить, какое значение применяется при одинаковом имени переменной группы и переменной playbook.

**Проверка:** Ansible подключается ко всем узлам; студент объясняет результат проверки переменных.

*Скриншот 17: доступность узлов и результат упражнения с переменными.*

### 18. 🔴 Развернуть и обновить Kubernetes через Kubespray

Развернуть Kubernetes на подготовленных виртуальных машинах.

После установки:

1. Проверить готовность узлов.
2. Проверить системные Pod.
3. Запустить небольшую контрольную нагрузку.
4. Выбрать поддерживаемый путь обновления по документации используемой версии Kubespray.
5. Выполнить обновление.
6. Повторить проверки.

Зафиксировать возникшие ошибки и перерывы в работе, если они были.

**Проверка:** кластер развёрнут и обновлён; контрольная нагрузка работает после изменения.

*Скриншот 18: версии узлов и результаты контрольной проверки.*
