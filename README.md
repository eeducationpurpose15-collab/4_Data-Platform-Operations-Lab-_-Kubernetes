# Data Platform Operations Lab — сопровождение инфраструктуры в Kubernetes

## Цель проекта

Создать учебный стенд для отработки задач работодателя: **сопровождать компоненты в Kubernetes, обновлять конфигурации через Helm, настраивать мониторинг и автоматизировать операции обслуживания через GitLab CI**.

Самостоятельно подготовить среду, развернуть объектное хранилище, проверить работу с учебными файлами, настроить наблюдение за состоянием компонентов.

**Исходные условия:** готового стенда у преподавателя нет. Инструменты устанавливаются, а конфигурации и учебные данные создаются по ходу выполнения проекта.

**Формат реализации:** Kubernetes запускается локально через Minikube с Docker. GitLab и GitLab Runner разворачиваются на виртуальной машине согласно П.З. 2.

**Интернет:** необходим для получения установочных файлов, образов и зависимостей. Работа без интернета возможна после их предварительной загрузки.

**Ограничение:** возможность совместного запуска компонентов зависит от ресурсов компьютера. При недостатке ресурсов используется общий компьютер группы. Небольшой стенд позволяет освоить операции сопровождения, но не воспроизводит масштаб высоконагруженной банковской платформы.

**Статус:** проект для реализации. Конфигурации, команды и результаты проверок создаются в ходе выполнения.

### Полученные навыки

* Организация проекта и хранение конфигураций в Git.
* Развёртывание GitLab и GitLab Runner.
* Автоматизация операций через GitLab CI.
* Использование виртуальных машин и Docker.
* Развёртывание и диагностика компонентов Kubernetes.
* Работа с S3-совместимым объектным хранилищем.
* Применение Ansible для настройки конфигураций.
* Изменение и обновление компонентов через Helm.
* Настройка мониторинга Prometheus и визуализации Grafana.
* Просмотр журналов и проверка работоспособности после изменений.

## Этапы выполнения

**Порядок обучения:** подготовить среду → запустить компонент → проверить → изменить конфигурацию → настроить мониторинг → автоматизировать.

### 1. 🟢 Создать репозиторий проекта

**Основание:** П.З. 1 «Git. Организация проекта».

Установить Git и создать локальный репозиторий.

Добавить:

1. README с целью проекта.
2. Папку конфигураций.
3. Папку сценариев обслуживания.
4. Папку результатов проверок.

Сделать первый коммит.

**Проверка:** файлы сохранены в репозитории, история изменений доступна.

*Скриншот 1: структура проекта и первый коммит.*

### 2. 🟢 Подготовить виртуальную машину и Docker

**Основание:** лекция 3.1; П.З. 6 «VM, Docker, LXC-контейнеры».

Создать Linux-виртуальную машину для последующего размещения GitLab и Runner.

В среде для локального Kubernetes установить Docker. Запустить тестовый контейнер.

Выполнить:

1. Посмотреть состояние контейнера.
2. Открыть его журнал.
3. Остановить контейнер.
4. Запустить повторно.

**Проверка:** виртуальная машина доступна, Docker запускает контейнеры.

*Скриншот 2: работающая виртуальная машина и тестовый контейнер.*

### 3. 🟢 Описать архитектуру стенда

**Основание:** лекция 2.1; Л.Р. 1 «Архитектура облачных, распределенных, микросервисных и гибридных ИС».

Описать назначение компонентов:

* Kubernetes размещает сервисы.
* Объектное хранилище хранит учебные файлы.
* GitLab Runner выполняет задания обслуживания.
* Prometheus собирает метрики.
* Grafana отображает состояние системы.

Указать, какие компоненты взаимодействуют и для чего.

**Проверка:** студент объясняет путь учебного файла от загрузки в хранилище до выполнения операции обслуживания.

*Скриншот 3: схема архитектуры.*

### 4. 🟢 Создать Kubernetes-кластер

**Основание:** лекция 3.2; П.З. 7 «Kubernetes»; Minikube предусмотрен П.З. 12–13.

Установить Minikube и `kubectl`. Запустить локальный кластер с Docker.

Выполнить:

1. Проверить готовность узла.
2. Посмотреть системные Pod.
3. Создать пространство имён проекта.
4. Сохранить инструкцию запуска.

**Проверка:** узел находится в состоянии `Ready`, системные компоненты работают.

*Скриншот 4: состояние кластера.*

### 5. 🟡 Развернуть объектное хранилище

**Основание:** лекция 3.4; П.З. 9 «DataLake, DataWareHouse, S3»; П.З. 7 «Kubernetes».

Выбрать реализацию S3-совместимого хранилища и подготовить минимальную конфигурацию запуска в Kubernetes.

Настроить:

1. Компонент хранилища.
2. Учебные учётные данные.
3. Постоянный том для данных.
4. Service для подключения.

Создать учебный бакет.

**Проверка:** хранилище доступно, бакет создан.

*Скриншот 5: состояние хранилища и учебный бакет.*

### 6. 🟡 Проверить операции с учебными файлами

**Основание:** лекция 3.4; П.З. 9.

Самостоятельно создать небольшой текстовый файл.

Выполнить:

1. Загрузить файл в учебный бакет.
2. Получить список объектов.
3. Скачать файл.
4. Сравнить содержимое с исходным.
5. Скопировать объект в другой учебный префикс.

**Проверка:** загруженный, скачанный и скопированный файлы содержат одинаковые данные.

*Скриншот 6: объекты и результат сравнения.*

### 7. 🟡 Автоматизировать настройку через Ansible

**Основание:** лекция 3.3; П.З. 8 «Ansible, Puppet».

Создать небольшой inventory и playbook для учебной виртуальной машины.

В playbook:

1. Создать рабочую папку.
2. Сформировать конфигурационный файл из шаблона.
3. Передать один параметр через переменную.
4. Применить настройку.
5. Повторить запуск.

**Проверка:** файл содержит заданное значение; повторное выполнение без изменения параметров не вносит лишних изменений.

*Скриншот 7: playbook и результат повторного запуска.*

### 8. 🟡 Изменить конфигурацию через Helm

**Основание:** лекция 4.2; П.З. 11 «Kubernetes: Helm-чарты и HPA».

Использовать подходящий Helm-чарт для компонента хранилища либо оформить его рабочие манифесты в небольшой чарт.

Выполнить:

1. Сохранить параметры в `values.yaml`.
2. Проверить сформированные манифесты.
3. Применить конфигурацию.
4. Изменить один параметр ресурсов.
5. Обновить компонент.

**Проверка:** новое значение применилось; загрузка и скачивание учебного файла работают.

*Скриншот 8: изменённый параметр и состояние компонента.*

### 9. 🟡 Настроить сбор метрик Prometheus

**Основание:** лекция 5.1; П.З. 12 «Prometheus в Minikube».

Установить Prometheus в Minikube. Подключить источники метрик компонентов и ресурсов Kubernetes.

Начать с небольшого набора:

1. Доступность источника метрик.
2. Использование CPU.
3. Использование памяти.
4. Перезапуски Pod.

**Проверка:** метрики поступают; студент находит показатели нужного компонента.

*Скриншот 9: полученные метрики.*

### 10. 🟡 Создать панель Grafana

**Основание:** лекция 5.2 «Визуализация в Grafana».

Установить Grafana и подключить Prometheus как источник данных.

Создать панель с показателями предыдущего этапа. Выполнить несколько загрузок и скачиваний файлов и проследить за изменением метрик.

**Проверка:** панель отображает фактические данные; студент объясняет назначение каждого показателя.

*Скриншот 10: панель мониторинга.*

### 11. 🟠 Найти причину проблемы Kubernetes

**Основание:** П.З. 7; раздел 5 «Мониторинг, наблюдаемость»; Л.Р. 4 «Обследование и логирование облачных систем».

Создать отдельную учебную копию конфигурации с запросом ресурсов, превышающим доступные ресурсы узла.

Выполнить:

1. Найти Pod в состоянии ожидания.
2. Посмотреть события Kubernetes.
3. Сопоставить запрос с ресурсами узла.
4. Исправить значение.
5. Повторить запуск.

Если контейнер ещё не запускался, искать причину в событиях планирования; журналы приложения появятся после его запуска.

**Проверка:** причина подтверждена сообщением Kubernetes, после исправления Pod запускается.

*Скриншот 11: событие с причиной проблемы и результат исправления.*

### 12. 🟠 Развернуть GitLab и GitLab Runner

**Основание:** П.З. 2 «Развёртывание GitLab и GitLab Runner на виртуальной машине»; лекция 1.2.

На подготовленной виртуальной машине:

1. Установить GitLab.
2. Создать проект.
3. Отправить в него локальный репозиторий.
4. Установить и подключить GitLab Runner.
5. Создать первое задание `.gitlab-ci.yml`.

Первое задание выводит короткое проверочное сообщение.

**Проверка:** Runner принимает задание, выполнение завершается успешно.

*Скриншот 12: успешный запуск задания.*

### 13. 🟠 Автоматизировать операцию с хранилищем

**Основание:** лекция 1.2; П.З. 2 и П.З. 9.

Перенести проверенную операцию копирования учебного файла в GitLab CI.

Выполнить:

1. Обеспечить доступ Runner к хранилищу.
2. Передать учётные данные через переменные CI.
3. Указать источник и назначение копирования.
4. Запустить задание.
5. Проверить полученный объект.

**Проверка:** операция выполняется автоматически, скопированный файл совпадает с исходным; секреты не выводятся в журнал.

*Скриншот 13: успешное задание и скопированный объект.*

### 14. 🟠 Проверить обновление компонента

**Основание:** лекция 4.2; П.З. 11; лекции 5.1–5.2.

Выполнить контролируемое обновление конфигурации через Helm.

До изменения сохранить текущие параметры и проверить доступность учебного файла.

После изменения:

1. Проверить состояние Pod.
2. Просмотреть события и журналы.
3. Посмотреть метрики.
4. Повторить загрузку и скачивание файла.
5. Запустить задание обслуживания в GitLab CI.

**Проверка:** обновлённый компонент работает, данные доступны, автоматизированная операция выполняется.

*Скриншот 14: результат обновления и контрольных проверок.*

### 15. Зафиксировать результат проекта

**Основание:** П.З. 1 «Git. Организация проекта».

Сохранить в репозитории:

* Инструкцию подготовки среды.
* Схему архитектуры.
* Конфигурации Kubernetes и Helm.
* Inventory и playbook Ansible без секретов.
* Конфигурацию GitLab CI.
* Настройки мониторинга.
* Результаты проверок и скриншоты.

Каждый выполненный этап описать по схеме:

**Задача → действия → проверка → результат.**

**Проверка:** другой участник может повторить выбранный этап по сохранённым файлам и инструкции.

*Скриншот 15: репозиторий и итоговый README.*

**Критерий завершения:** объектное хранилище работает в Kubernetes; конфигурация изменяется через Helm; Prometheus и Grafana показывают состояние компонентов; причина учебного сбоя установлена; GitLab CI выполняет операцию обслуживания; результаты сохранены в Git.

**Главный отрабатываемый навык: сопровождение инфраструктуры в Kubernetes — настройка, мониторинг, диагностика и автоматизация обслуживания.**
